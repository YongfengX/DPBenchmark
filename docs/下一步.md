## 接下来做什么

按顺序做，前一步不过不要往后走。

### 1. 在有环境的机器上跑测试（不需要 GPU）

```bash
git clone https://github.com/YongfengX/DPBenchmark.git && cd DPBenchmark
pip install -e ".[dev]"        # 需要 Python 3.11 以上
pytest
```

原有 53 个测试加上 `test_vllm_step_trace.py` 的 10 个应当全部通过。有失败就先修，再继续。

### 2. 给 vLLM 打补丁并启动（4 × L40S）

步骤和启动命令见 [adapters/vllm/v0.32.0/README.md](../adapters/vllm/v0.32.0/README.md)。启动后确认日志里：

- 每个 rank 有一行 `dpbench step trace on for DP rank k`；
- 没有 `dpbench step trace is off` 的警告（有就说明 async scheduling 没关掉）；
- MoE 后端是 Triton FP8 或 BF16，all2all 后端是 `allgather_reducescatter`。

### 3. 发一个请求，确认回放器的假设

用 `/v1/completions`，token id 形式的 `prompt`，`max_tokens = min_tokens = N`，`ignore_eos = true`，
带请求头 `X-data-parallel-rank: 2`。确认：

- `usage.completion_tokens` 等于 N；
- `cached_tokens` 为 0；
- 只有 `step.rank2.csv` 出现非 dummy 的行，其余 rank 全是 dummy；
- rank 2 的 `prefill_tokens + decode_tokens` 总和等于 `输入长度 + N − 1`。
  不等的话，`metrics.check_step_work` 里的“减 1”要改。

### 4. 跑第一次回放并合并 step 表

```bash
dpbench gen --scenario D2 --n 50 --rate 100 --seed 1 --copies 4 --mode test --out wl/test.jsonl
dpbench replay --workload wl/test.jsonl --manifest examples/manifest.4xL40S.vllm-0.32.json --policy rr --out runs/rr-0
dpbench merge-steps runs/rr-0 --trace-dir <DPBENCH_STEP_TRACE_DIR>
dpbench validate runs/rr-0 && dpbench metrics runs/rr-0
```

`merge-steps` 以 0 退出，就说明对齐检查和工作量守恒检查都过了，“step_id 对齐假设”这一项可以划掉。

### 5. 定两件事

- `vllm_default` 策略：v0.32.0 的内部均衡公式已经变了，回放器能模拟的部分与 `jsq` 相同。
  删掉这个模拟只用 `server` 策略，还是保留并改公式。
- 开着 CUDA Graph 时各 rank 的 token 数会被补齐到最大值，负载轻的 rank 是“陪着算”而不是“等”。
  “同步等待损失”和空等占比 W 的定义要不要跟着改，在设计文档里定一个说法。
  可以先用第 4 步的数据看一眼：各 rank 同一步的时长是否几乎相同。

### 6. S3 剩下的部分

- 补 AgentX 多轮会话的加载器（场景 P3）。
- 跑 D1、D2、P2 和 lag 运行，用 RR 和 JSQ 两个策略，每个配置重复多次。
- 过关条件：工作量守恒检查通过；噪声地板（V1）和零点（V2）通过；lag 运行测得出吞吐下降。
- DP 1 与 DP 4 对同一批请求的输出逐 token 比对。
- 埋点开销（V5）：同一配置开关 `DPBENCH_STEP_TRACE_DIR` 各跑一次，吞吐下降不超过 0.5%。
- layer 埋点（L2），只在单独的 `--enforce-eager` 运行里采。
